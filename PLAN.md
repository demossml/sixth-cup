# План доработки «6.7 Coffee» до полноценного приложения

Точка отсчёта: офлайн-протокол, три механики (карта-стакан, реферальный кэшбэк, промо), касса и клиент — уже работают и проверены сценарием из гайда. Дальше — то, что отделяет рабочий прототип от того, что можно поставить в реальную кофейню и не бояться.

Порядок фаз важен: сначала то, без чего приложение просто не переживёт первый день в проде (безопасность ключей, бэкапы), потом — то, без чего неудобно работать (админка, обучение персонала), и только потом — красота и рост.

---

## Фаза 0. Подготовка (перед всем остальным)

- [ ] Прогнать `npm install` + `npm run typecheck` на текущем коде — убедиться, что мои последние правки (переименование `emoji`→`icon`) ничего не сломали.
- [ ] Удалить `backend/data` и один раз пройти полный сценарий из гайда вручную (клиент + касса, офлайн и синк) — зафиксировать, что всё ещё работает после правок.
- [ ] Завести git-репозиторий, если ещё нет. Один коммит = один сохранённый рабочий срез, дальше двигаться маленькими шагами.

## Фаза 1. Надёжность и безопасность (обязательно до первого реального клиента)

Это код, который не видно, но без которого одна ошибка обнулит все карты клиентов или сольёт данные.

- [ ] **Продовые секреты.** `JWT_SECRET`, `ADMIN_TOKEN` — сгенерировать длинные случайные значения, положить в `.env` на сервере (уже есть защита «не стартует без них» — проверить, что она реально сработает).
- [ ] **Бэкап `backend/data/keys.json` и базы.** Это самое критичное: потеря `keys.json` = все выданные карты клиентов становятся недействительными. Настроить автоматический ежедневный бэкап (cron + копия в другое место, не на том же диске).
- [ ] **HTTPS.** Без него не будет ни PWA, ни камеры на телефоне. Поднять Caddy или nginx + Let's Encrypt перед сервером.
- [ ] **Rate limiting на `/api/auth/send-code`.** Сейчас ничего не мешает боту слать тысячи SMS-запросов на случайные номера — это расходы на SMS и вектор злоупотребления. Добавить лимит (например, 3 запроса на телефон в час, через IP тоже).
- [ ] **Реальная отправка SMS.** Сейчас код показывается на экране в dev-режиме. Подключить провайдера (SMS.ru, SMSC.ru, Devino — сравнить цены под объём кофейни). Важно: в `config.ts` уже есть переключатель `isDev` — просто добавить вызов провайдера в ветку `!isDev`.
- [ ] **Ограничение попыток ввода кода.** Сейчас код можно подбирать (4 цифры = 10 000 вариантов). Добавить счётчик неудачных попыток и блокировку номера на время.
- [ ] **Тесты на ядро логики.** Минимум: `freeAvailable`, `couponDiscount`/`discountFor`, `applyReceipts` (двойная отправка чека, чек с неверной подписью, чек от отозванной кассы). Это единственная часть системы, где баг стоит реальных денег.
- [ ] **Что делать при краже кассы.** Проверить, что `POST /api/admin/devices/:id/revoke` действительно блокирует приём чеков от этого устройства (кассовый ключ лежит в браузере планшета — если его украли, чеки с него не должны приниматься).

## Фаза 2. Инструменты для владельца (без веб-панели с `curl` жить нельзя)

Сейчас управление кофейней — это ручные запросы через терминал. Это нормально для теста, но не для реальной работы каждый день.

- [ ] **Веб-панель администратора** (отдельная страница, доступ по паролю/токену): список касс + кнопка «выпустить код регистрации» + кнопка «отозвать»; список товаров с формой добавления/редактирования; список акций с формой создания/удаления и предпросмотром, как акция будет выглядеть в приложении; список споров (`disputes`) с понятной расшифровкой, что произошло.
- [ ] **Отчёты.** Сколько чеков за день/неделю, сколько выдано бесплатных стаканов, сколько кэшбэка начислено и списано, сколько новых клиентов и по чьим приглашениям. Без этого владелец не увидит, работает ли программа лояльности.
- [ ] **Экспорт в CSV** хотя бы для базовых таблиц (`orders`-аналог не нужен, а вот `receipts`/`cashback_ledger` — да) — для бухгалтера.

## Фаза 3. Касса и персонал (то, от чего зависит, будут ли этим вообще пользоваться)

- [ ] **Пошаговая инструкция для бариста на одном листе А4**: «отсканируй карту → введи количество стаканов и сумму → покажи чек клиенту». Уже есть логика — не хватает физической памятки на кассу.
- [ ] **Отдельный сценарий «касса без интернета весь день».** Проверить: сколько чеков может накопиться в очереди без переполнения `IndexedDB`, что видит кассир, если справочник (`directory`) устарел на несколько дней.
- [ ] **Защита от ошибок кассира.** Например, повторное сканирование той же карты подряд — сейчас это создаст два чека. Добавить короткое окно («эта карта уже пробита 10 секунд назад, точно ещё раз?»).
- [ ] **Второе кассовое устройство на точку** (на случай, если планшет разрядился/сломался) — сценарий уже поддержан (`/api/admin/devices`), нужно только проверить его на практике.

## Фаза 4. Клиентский опыт (полировка интерфейса)

Из предыдущего разбора — три пункта, которые сделают приложение более «настоящим»:

- [ ] Плитки быстрых действий на главном экране вместо вертикального списка ссылок.
- [ ] Более заметная «карта участника» (визуально — как пластиковая карта, а не просто прогресс-бар).
- [ ] Крупнее карточки акций/рекламы партнёров.

Плюс новое:
- [ ] **Онбординг в 2–3 экрана** перед первым входом: коротко объяснить три механики (карта, кэшбэк за друга, акции) — сейчас это всё написано мелким текстом на экране логина.
- [ ] **Пустые состояния** (empty states) — что видит человек, если у него ещё нет купонов/друзей/кэшбэка: сейчас есть текст-заглушка, можно сделать нагляднее (иллюстрация + понятный призыв к действию).
- [ ] **Тёмная тема** — раз приложение работает как настоящий PWA, разумно поддержать `prefers-color-scheme`.

## Фаза 5. Устойчивость сети и синхронизации

- [ ] **Что видит клиент, если два офлайн-чека противоречат друг другу** (уже частично обработано через `disputes`, но фронтенд никак не показывает клиенту, что был спорный случай). Решить: молчать и просто исправлять на сервере (текущее поведение) или как-то уведомлять — вероятно, молчать правильнее, но стоит осознанно это зафиксировать, а не оставить как есть по умолчанию.
- [ ] **Уведомления в приложении**, если Web Push окажется нужен (например, «начислен кэшбэк от друга») — раньше не было критично, но для вовлечения полезно. Требует HTTPS и добавления service worker push-обработчика.
- [ ] **Автообновление справочника чаще, чем раз в минуту**, если сеть есть, но нестабильна — сейчас интервал синка фиксирован, можно сделать адаптивным.

## Фаза 6. Рост и вовлечение (когда база уже стабильна)

- [ ] **Второй канал приглашения** — не только ссылка, но и QR-код на самой кофейне (наклейка на столе), который сразу открывает регистрацию с предзаполненным кодом приглашения точки/сотрудника.
- [ ] **Именные пуш/баннеры** («до бесплатного стакана осталось 2») — по сути уже считается на клиенте (`freeAvailable`/`progress`), не хватает только более заметного визуального акцента, когда до подарка близко.
- [ ] **Сегментация акций по точкам** — сейчас акции общие для всех кофеен, можно добавить привязку акции к конкретной точке (partner-промо у одной кофейни может не подойти для другой).

## Фаза 7. Юридическое (сделать до масштабирования, не после)

- [ ] Политика конфиденциальности и согласие на обработку персональных данных (152-ФЗ): вы храните телефоны, историю чеков, геопривязку к точкам. Проконсультироваться с юристом — я не даю здесь юридических консультаций, только напоминаю, что это нужно сделать.
- [ ] Оферта на программу лояльности (условия начисления/сгорания кэшбэка и купонов) — по закону должны быть публично описаны.
- [ ] Проверить требования к хранению данных на серверах в РФ, если это применимо к вашей юрисдикции размещения.

## Как двигаться по плану

Рекомендуемый порядок: **Фаза 1 → Фаза 3 → Фаза 2 → Фаза 7 → Фаза 4 → Фаза 5 → Фаза 6.**
Логика: сначала не потерять данные и не подставиться под расходы на SMS-спам (Фаза 1), затем — обучить первую кофейню реально этим пользоваться (Фаза 3), затем дать себе инструмент управления без терминала (Фаза 2), закрыть юридические риски до масштабирования (Фаза 7), и только потом — полировка и рост (Фазы 4–6).

Дальше можно двигаться по одному пункту за раз: скажи, с какого начинаем (например, «сделай rate limiting на send-code» или «веб-панель администратора»), и я сделаю прямо в присланном проекте.
