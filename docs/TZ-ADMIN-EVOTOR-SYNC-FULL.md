# ТЗ: Админка 6.7 Coffee + backend-синхронизация с Эвотор Cloud

**Версия:** 1.0  
**Область:** только веб-админка владельца + backend.  
**Вне области этой версии:** APK-касса (кроме косвенного эффекта номенклатуры), клиентское PWA-лояльность (6-й стакан, кэшбэк, QR), SMS, enroll устройств 6.7.

---

## 1. Цель

Владелец в админке:

1. Видит **реальные торговые точки и сотрудников** из Эвотор Cloud (только чтение).
2. Создаёт **свои** товары и **свои** группы (меню 6.7): рецепт, фото, описание, цена, добавки и т.д.
3. Указывает **на каких точках** товар продаётся (галочки).
4. Backend **один раз** создаёт позицию в номенклатуре Эвотор на каждой выбранной точке, сохраняет **Evotor UUID**, дальше только **обновляет**.
5. Backend **забирает документы продаж (SELL и др.)** из Cloud и привязывает строки чека к **нашим** товарам по UUID.
6. Иерархия меню совпадает с моделью Эвотор: **группа (parent) → товары**.

Одна бизнес-схема данных, без «двух разных миров» (ручные магазины 6.7 vs Эвотор).

## 2. Два источника правды

### 2.1. Эвотор Cloud — источник

| Данные | Мы | Действия |
|--------|-----|----------|
| Торговые точки (stores) | Копия в нашей БД | Только **GET** из API, отображение |
| Сотрудники (employees) | Копия | Только **GET** |
| Номенклатура Cloud | Читаем для сверки / поиска uuid | **Не** превращаем автоматически в товары 6.7 |
| Документы (SELL, PAYBACK, …) | Копия + разбор | **GET** поллинг, запись продаж 6.7 |
| UUID товара/группы в Cloud | Храним в связях | После CREATE — постоянный ключ |

### 2.2. 6.7 — источник

| Данные | Где | Примечание |
|--------|-----|------------|
| Группы меню (Кофе, Чай…) | Наша БД | Создаём мы; при sync — группа в Эвотор |
| Товары (карточка) | Наша БД | Один товар — одна запись |
| Рецепт, фото, описание, топпинги | Наша БД | В кассу — через ProductExtra, когда дойдём |
| Цена | Одна на товар (все точки) | Пока без цен по точкам |
| Назначения «где продаётся» | `product_store_links` | Галочки в UI |
| Стаканы/loyalty | **Не в этом ТЗ** | Код может жить, админка loyalty не использует |

## 3. Модель данных (коллекции / таблицы)

Ниже — логические сущности. Имена таблиц можно уточнить в миграциях, смысл полей обязателен.

### 3.1. `evotor_stores` (точки из Cloud)

| Поле | Тип | Описание |
|------|-----|----------|
| `uuid` | TEXT PK | UUID магазина в Эвотор |
| `name` | TEXT | Название **только** из API |
| `address` | TEXT NULL | Если API отдаёт |
| `code` | TEXT NULL | Код магазина, если есть |
| `raw_json` | TEXT NULL | Опционально снимок ответа |
| `updated_at` | INTEGER | Время последнего upsert из API |

**Запрещено в UI:** создать точку, переименовать, удалить «у нас». Удаление/переименование — только в ЛК Эвотор, у нас обновится при следующем sync stores.

### 3.2. `evotor_employees` (сотрудники)

| Поле | Тип | Описание |
|------|-----|----------|
| `uuid` | TEXT PK | UUID сотрудника |
| `name` / `last_name` / … | TEXT | Как отдаёт API |
| `store_uuid` | TEXT NULL | Если привязан к точке |
| `updated_at` | INTEGER | |

Только синхронизация и просмотр.

### 3.3. `product_groups` (группы 6.7 = группы Эвотор)

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INTEGER PK | Наш id |
| `name` | TEXT | «Кофе», «Чай»… |
| `sort_order` | INTEGER | Порядок в меню |
| `evotor_uuid` | TEXT NULL | UUID **группы** в Cloud (после CREATE group) |
| `created_at` / `updated_at` | INTEGER | |

Группа создаётся **сначала у нас**, затем при необходимости в Cloud.  
В Эвотор у товара поле **parent** = `evotor_uuid` этой группы.

### 3.4. `products` (карточка товара 6.7)

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INTEGER PK | Наш id |
| `name` | TEXT | Название |
| `price` | INTEGER | Цена в **копейках** (единая для всех точек) |
| `group_id` | INTEGER FK → product_groups | Группа меню |
| `description` | TEXT NULL | |
| `image_url` | TEXT NULL | Фото (наш storage/URL) |
| `recipe_text` | TEXT NULL | Рецепт |
| `recipe_cost_rub` / `recipe_seconds` | NULL | Техпараметры |
| `modifier_scheme_id` | NULL | Схема добавок, если есть |
| `tax` | TEXT | Напр. `NO_VAT`, `VAT_20` |
| `measure` | TEXT | `шт`, `кг`… |
| `cost_price_kopecks` | INTEGER NULL | Себестоимость |
| `available` | INTEGER 0/1 | Доступность в 6.7 |
| `counts_as_cup` | INTEGER 0/1 | На будущее loyalty; в админ-контуре можно хранить |
| `article_number` | TEXT | Стабильный артикул, напр. `sc-{id}` |
| `evotor_extra_json` | TEXT NULL | JSON для ProductExtra |
| `created_at` / `updated_at` | INTEGER | |

**Не создаём** отдельную строку `products` на каждую точку.

### 3.5. `product_store_links` (назначение на точку + uuid в Cloud)

| Поле | Тип | Описание |
|------|-----|----------|
| `product_id` | INTEGER | FK products |
| `store_uuid` | TEXT | FK логический на evotor_stores.uuid |
| `evotor_uuid` | TEXT NULL | UUID **товара** в номенклатуре **этого** магазина |
| `enabled` | INTEGER 0/1 | Галочка «продаётся здесь» |
| `allow_to_sell_remote` | INTEGER 0/1 | Последнее известное состояние в Cloud |
| `last_synced_at` | INTEGER NULL | |
| `last_error` | TEXT NULL | Текст ошибки sync |
| `created_at` / `updated_at` | INTEGER | |
| PRIMARY KEY | `(product_id, store_uuid)` | |

Смысл:

- `enabled=1`, `evotor_uuid IS NULL` → нужен **CREATE** в Cloud.  
- `enabled=1`, `evotor_uuid IS NOT NULL` → **UPDATE**.  
- `enabled=0`, uuid был → **UPDATE** `allow_to_sell=false`, uuid **не** затираем.  
- Снова `enabled=1` → UPDATE `allow_to_sell=true`, **без** нового CREATE.

### 3.6. `evotor_documents` (сырые / разобранные документы)

| Поле | Тип | Описание |
|------|-----|----------|
| `store_uuid` | TEXT | |
| `doc_id` | TEXT | Id документа в Эвотор |
| `type` | TEXT | `SELL`, `PAYBACK`, … |
| `close_date` | TEXT/INTEGER | |
| `payload_json` | TEXT | Полный документ или сжатое тело |
| `processed_at` | INTEGER NULL | Когда разобрали в продажи 6.7 |
| PRIMARY KEY | `(store_uuid, doc_id)` | |

### 3.7. `evotor_sync_state` (курсор поллинга)

| Поле | Тип | Описание |
|------|-----|----------|
| `store_uuid` | TEXT PK | |
| `last_seen_close_ms` / date | | Нижняя граница следующего запроса документов |
| `last_poll_at` | INTEGER | |
| `last_error` | TEXT NULL | |

### 3.8. `sales_lines` (опционально, удобно для UI «Продажи»)

Нормализованная продажа для админки:

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INTEGER PK | |
| `store_uuid` | TEXT | |
| `doc_id` | TEXT | |
| `product_id` | INTEGER NULL | Наш id, если нашли по uuid |
| `evotor_product_uuid` | TEXT | uuid позиции в чеке |
| `name_snapshot` | TEXT | Имя из чека |
| `qty` | REAL | |
| `sum_kopecks` | INTEGER | |
| `closed_at` | INTEGER | |

Поиск нашего товара:

```
product_store_links
  WHERE store_uuid = ? AND evotor_uuid = productUuid_из_чека
→ product_id
```

Не по названию «Капучино».

### 3.9. Чего больше нет в рабочем контуре админки

- Ручной справочник `stores` как «наш бизнес-магазин» с кнопкой «Новая точка».  
- Обязательный enroll-касс 6.7 для этой схемы.  
- Авто-`INSERT` в `products` из любого товара Cloud (`catalog_source = EVOTOR_IMPORT`) как основной поток.

Старые таблицы могут остаться в БД для совместимости, но UI и worker их не используют как источник точек.

## 4. API Эвотор (что дергаем)

База: `https://api.evotor.ru`  
Заголовок: `X-Authorization: <EVOTOR_API_TOKEN>` (только server `.env`, не в Git, не в браузер).

| Операция | Метод (ориентир v1 inventories) | Назначение |
|----------|-----------------------------------|------------|
| Список магазинов | `GET .../inventories/stores/search` | Точки |
| Сотрудники | `GET .../employees/search` (или актуальный path из FACTS) | Сотрудники |
| Товары магазина | `GET .../inventories/stores/{storeUuid}/products` | Сверка, поиск |
| Создать/залить товары | `POST .../inventories/stores/{storeUuid}/products` | CREATE/массив |
| Обновление | POST/PUT того же контура по uuid | UPDATE |
| Группы | POST product-groups / аналог по доке | Группа + parent |
| Документы | `GET .../stores/{storeUuid}/documents?gtCloseDate&ltCloseDate` | Продажи |
| ProductExtra | POST extras (когда подключим рецепт на кассу) | Метаданные 6.7 |

Точные path/форматы дат — по `EVOTOR-FACTS.md` на проде (уже проверено: даты `YYYY-MM-DD`).

## 5. Синхронизация: что, когда, как

### 5.1. Точки и сотрудники (входящая)

**Триггеры:** кнопка «Обновить из Эвотор»; опционально раз в N часов cron.

```
Evotor API stores/employees
    → upsert evotor_stores / evotor_employees
    → админка читает только эти таблицы
```

Поля имени/адреса **перезаписываются** ответом API (источник — Эвотор).

### 5.2. Группы и товары (исходящая, мы → Cloud)

**Триггер:** «Сохранить» карточку товара / «Синхронизировать» / фоновый worker.

Алгоритм на **каждую** строку `product_store_links` с `enabled=1`:

1. Убедиться, что у `product_groups` есть `evotor_uuid` на этой логике магазина (если группы в Эвотор per-store — создать группу в магазине; если global — по факту API).  
2. Если `evotor_uuid` товара NULL:  
   - POST product с `name`, `price/100`, `tax`, `measureName`, `articleNumber=sc-{id}`, `parentUuid=group.evotor_uuid`, `allowToSell=true`.  
   - Сохранить возвращённый uuid в `product_store_links.evotor_uuid`.  
3. Если uuid есть:  
   - UPDATE те же поля + `allowToSell` по `enabled`.  
4. При timeout после CREATE: поиск в GET products по `article_number`, привязать uuid, не плодить дубль.  
5. Ошибку писать в `last_error`.

**Снятие галочки:** UPDATE `allowToSell=false`, uuid сохранить.

**Повторная галочка:** UPDATE `allowToSell=true`.

### 5.3. Документы продаж (входящая)

**Триггер:** `PollService` каждые N секунд (если токен задан) + ручной «Poll» в настройках.

```
Для каждого store_uuid из evotor_stores:
  GET documents (окно дат по sync_state)
  → upsert evotor_documents
  → для type=SELL разобрать transactions / positions
  → по productUuid + store_uuid найти product_id
  → upsert sales_lines
  → сдвинуть sync_state
```

На этом этапе **не** обязательно начислять loyalty; достаточно видеть продажи в админке.

### 5.4. Что синхронизируем «полностью»

| Сущность | Полностью? | Комментарий |
|----------|------------|-------------|
| Магазины | Да, список из API | Копия для UI и assignments |
| Сотрудники | Да, список | Просмотр |
| Товары 6.7 → Cloud | Только назначенные на точку | Не весь чужой ассортимент Эвотор |
| Номенклатура Cloud → products 6.7 | **Нет** автоматом | Только ручное сопоставление позже, если понадобится |
| Документы | Да, в выбранном окне дат | SELL и служебные типы по мере надобности |
| Остатки quantity | Не цель v1 админки | Можно читать, не вести у себя как ERP |

## 6. Админка: экраны и поведение

### 6.1. Меню

1. **Обзор** — счётчики: точек, товаров 6.7, связей с uuid, ошибок sync, время last poll.  
2. **Точки** — read-only список Эвотор + «Обновить».  
3. **Товары** — CRUD 6.7 + галочки точек.  
4. **Группы** — CRUD групп.  
5. **Продажи** — агрегаты за день / последние документы.  
6. **Настройки → Эвотор** — статус токена (да/нет), last sync, ошибки, кнопки sync/poll.  

Не в главном меню: Кассы enroll, loyalty, «Новая точка».

### 6.2. Карточка товара

Поля: имя, цена, группа, описание, фото, рецепт, добавки, налог, единица, себестоимость, available.

Блок **«Где продаётся»:** чекбоксы по `evotor_stores`.

Кнопка **Сохранить** → БД + постановка в очередь sync (или sync сразу).

Индикаторы по каждой точке: «не в Cloud» / «uuid …» / «ошибка: …».

### 6.3. Клиентское приложение (следующий слой, но схема одна)

Когда вернётесь к PWA:

- Каталог строить **группа → товары** из наших `product_groups` + `products` (и/или после sync — те же uuid, что в Эвотор).  
- Не заводить отдельное «плоское» меню вразрез с parent/uuid.

Это ТЗ админки **не** меняет клиентский код сейчас, но фиксирует целевую модель.

## 7. Поля, уходящие в Эвотор при CREATE/UPDATE товара

**Стандартные (касса):**

- `uuid` (при update — существующий; при create — сгенерировать или принять от API)  
- `name`  
- `price` (рубли, float)  
- `measureName` / `measure_name`  
- `tax`  
- `allowToSell` / `allow_to_sell`  
- `articleNumber` = `sc-{product.id}`  
- `parentUuid` = uuid группы  
- `group: false`, `type: NORMAL` (или SERVICE — по типу)  
- `quantity` — по политике (часто большое число или 0 для услуги)

**Наши (ProductExtra / extras JSON), не вместо кассовых полей:**

- recipe, toppings, description, image url, countsAsCup, internal product id  

Касса фискалит по стандартным полям; extra — для приложения/рецепта.

## 8. Сценарии end-to-end

### 8.1. Новый товар на две точки

1. Админ создал группу «Кофе» → sync группы → `product_groups.evotor_uuid`.  
2. Создал «Капучино 300», 220 ₽, группа Кофе.  
3. Галочки: Смоленск ТРЦ, Центр.  
4. Backend: 2 строки links, uuid NULL.  
5. CREATE в каждом store → два **разных** evotor uuid (номенклатура **по магазинам**).  
6. Сохранили связи.  
7. На терминалах после загрузки номенклатуры товар виден.

### 8.2. Смена цены

1. 220 → 230 в карточке.  
2. Для каждого link с uuid → UPDATE price.  
3. CREATE не вызывается.

### 8.3. Сняли точку

1. Галочка Москва снята → `enabled=0`.  
2. UPDATE allow_to_sell=false для uuid Москвы.  
3. История uuid сохранена.

### 8.4. Продажа

1. На кассе пробили Капучино.  
2. SELL в Cloud.  
3. Poll записал document.  
4. productUuid → link → product_id 157.  
5. В «Продажи»: Смоленск, Капучино, 1, 220 ₽.

## 9. Ошибки и идемпотентность

- Повторный sync не создаёт второй товар, если uuid или article_number уже в Cloud.  
- 402 «application not paid on store» — показать по точке, не ретраить бесконечно.  
- Нет токена — sync disabled, в UI «нет EVOTOR_API_TOKEN».  
- Документ обрабатывается один раз (PK store+doc_id).

---

## 10. Безопасность

- `EVOTOR_API_TOKEN` только на сервере.  
- Админка: `X-Admin-Token` / существующая auth владельца.  
- Токен не отдавать во frontend bundle.

---

## 11. Критерии приёмки

1. В админке нельзя создать торговую точку вручную; список = Эвотор.  
2. Товар один в БД; галочки пишут только links.  
3. После sync у link заполнен `evotor_uuid`; повторный sync не плодит дубли.  
4. Снятие галочки не удаляет uuid.  
5. Poll пишет документы; продажа находится по uuid, не по имени.  
6. Рецепт/фото остаются в нашей карточке после sync.  
7. Loyalty/APK/PWA в этом релизе не обязательны для приёмки админки.

## 12. Краткий ответ на «что синхронизируем»

| Направление | Сущности |
|-------------|----------|
| Эвотор → 6.7 | Магазины, сотрудники, **документы** (продажи), при необходимости read-only номенклатура Cloud для сверки |
| 6.7 → Эвотор | **Группы и товары** только на **выбранные** точки (CREATE один раз, далее UPDATE) |
| Не синхронизируем как поток | Авто-импорт всего чужого ассортимента Эвотор в наши products; ручные «наши магазины» |
