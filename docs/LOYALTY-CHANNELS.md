# Каналы записи лояльности (L-02)

Документ отвечает на один вопрос: **кто и как пишет состояние лояльности**, и при каких условиях
можно включать второй writer. Основание — аудит `RESEARCH-LOYALTY-AUDIT-67-FINAL.md`, дефект L-02.

## Действующая схема: один writer

Текущий APK кассы (`demossml/evotor-app`) пишет лояльность **только** одним путём:

1. `POST /api/devices/loyalty/resolve` — идентификация гостя и резерв бонусов.
2. APK кладёт `extras.sc` в фискальный чек Эвотора (`CardSession.extras`): `{v:2, c, ts, kind, op?, free, cb}`,
   продублированный под `extras[APP_UUID].sc` и плоским `extras.sc`.
3. `PollService` читает чек из Evotor Cloud и вызывает `handleSell` / `handlePayback`.

**APK не вызывает** `POST /api/devices/sales` и `POST /api/devices/sync`. Это подтверждено исходником
(`app/src/main/java/ru/sixthcup/evotor/net/LoyaltyApi.kt` — единственный loyalty-эндпоинт это `loyalty/resolve`;
продажу открывает штатный `SellLauncher` → фискальный документ Эвотора).

### Ключи дедупликации по каналам

| Канал | Где | Ключ |
|---|---|---|
| Evotor poll (SELL/PAYBACK) | `integrations/evotor/processing/SellHandler.ts` | PK `loyalty_ops(doc_store, doc_id)` |
| Online sale | `modules/devices/sales.ts` | `receipts.id = "<deviceId>:<fiscalId>"` |
| Receipt-sync (`/api/devices/sync`, `/api/sync`) | `modules/loyalty/receipts.ts` | PK `receipts.id = "<deviceId>-…"` |
| Ledger-строки | `loyalty_ledger` | `UNIQUE(source_type, source_id, card_id, operation)` |

Общего ключа между Evotor-чеком и `receipts.id` **нет**. Поэтому один и тот же физический чек,
принятый двумя каналами, применится дважды.

## Правила включения второго writer

Второй канал можно включать только при выполнении **всех** пунктов:

1. **Канонический фискальный идентификатор.** Оба канала обязаны писать один и тот же ключ:
   `fiscalId` из Эвотора (номер смены + номер чека + дата, либо `fiscalSign` ФН), а не внутренний
   `deviceId:fiscalId`. Ключ хранится в отдельной колонке `receipts.fiscal_key` с UNIQUE.
2. **Проверка перед записью.** Вставка `INSERT … ON CONFLICT DO NOTHING` по `fiscal_key`; при
   конфликте второй канал не начисляет и пишет `disputes(kind='cross_channel_duplicate')`.
3. **Согласованный набор дельт.** Если оба канала видели чек, дельты берутся из одного источника
   (тот, что выиграл вставку), второй не «досчитывает».
4. **Наблюдение.** Отчёт «сколько чеков пришло в двух каналах за сутки» до включения — ноль,
   после — метрика с алертом.

До выполнения всех четырёх пунктов второй writer не включается. Тяжёлый уникальный индекс
на существующей истории **не** добавляется: нужен миграционный план с проверкой дублей.

## Почему не «просто добавить unique» на текущих данных

Исторические строки `receipts` и `loyalty_ops` уже содержат данные разных форматов ключа.
Уникальный индекс по ним либо не создастся, либо потребует ручного сопоставления чеков,
что без фискальных признаков невозможно. Это отдельная задача уровня миграции, а не побочная
правка.

## Что считается безопасным сегодня

- Ручной ввод суммы/чека в админке — не пишет лояльность.
- Админская выдача ваучеров — не пересекается с чеками.
- Повторная обработка Evotor-документов после ретрая — безопасна: ключ `(doc_store, doc_id)`.
