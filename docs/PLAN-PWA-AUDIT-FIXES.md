# План: довести PWA до состояния из аудита главной — без регрессов

Источник: `~/67coffee-audit/report.md` (аудит 11.11.2026), раздел 14 — что уже сделано.
Область: только клиент `frontend/` (PWA гостя). Админка, касса и бэкенд не трогаются, кроме
точечных правок, если без них не решается задача.

---

## 0. Принципы

1. **Сначала проверка, потом правка.** В отчёте 4 находки из 15 не подтвердились по коду
   (уже зафиксировано в разделе 14 отчёта). Оставшиеся находки перепроверяем на **production-сборке**
   (`npm run build -w frontend && npm run preview`), а не только на dev — часть поведения (SW, офлайн,
   видео) на dev отличается.
2. **Инварианты, которые нельзя сломать** (проверяются после каждой фазы):
   - карта создаётся автоматически, без анкеты; путь «холодный старт → QR» = 2 тапа;
   - QR-слой: `role="dialog"`, `aria-modal`, фокус внутри, Escape и тап-мимо закрывают;
   - повторный запуск работает офлайн, карта и QR из кеша, есть индикатор «Офлайн»;
   - вёрстка не ломается на 320×568 и landscape 844×390, тапы ≥ 44 px, safe-area учтён;
   - сборка остаётся PWA: manifest + SW + иконки, установка не обязательна.
3. **Один коммит — одна находка.** Так любую правку можно откатить, не задев соседние.
4. **Решения владельца отделяем от реализации.** Спорные пункты (размер QR, порядок блоков,
   заголовок hero) идут как «решение → реализация», а не «сделали, как показалось».

## Фаза 0. Сверка (0,5 дня)

**Цель:** не тратить время на несуществующие дефекты и не «чинить» то, что уже работает.

1. Собрать прод-сборку и поднять preview: `npm run build -w frontend`, затем preview-сервер.
2. Пройти чек-лист состояний (по разделу 5 отчёта) и зафиксировать «подтверждено / иначе / не воспроизводится»:
   - офлайн-первый-визит: онбординг → «Пропустить» → есть ли экран «Нужен интернет один раз» + «Повторить»
     (в коде `RequireSession` такой экран есть — надо понять, почему аудит его не увидел);
   - hero: это `<video>` или картинка (`heroBackground` → `media()`), есть ли `poster`;
   - QR на карте (112 px) против QR в слое (440 px) — что реально сканируется на кассе;
   - `/onboarding` при уже созданной карте;
   - 320×568, 390×844, 844×390.
3. Результат — обновлённая таблица статусов в этом файле + скриншоты в `~/67coffee-audit/shots/`.
4. **Гейт:** дальше идём только с находками, подтверждёнными на прод-сборке.

## Фаза 2. Состояния и QR (1,5 дня)

1. **F-01 — первый визит офлайн.**
   - Воспроизвести на прод-сборке с SW.
   - Если экрана нет: показывать его **до** онбординга (или после «Пропустить») с текстом
     «Нужен интернет один раз — карта и QR появятся сами» и кнопкой «Повторить».
   - Если экран есть, но не виден: починить переход (онбординг «Далее/Пропустить» → честный статус).
   - Проверка: чистый профиль + Offline → экран с кнопкой; после включения сети «Повторить» создаёт карту.
2. **F-10 — размер QR (нужно решение владельца).**
   - Вариант A: оставить 112 px как «якорь» (текущая идея) — тогда переименовать подпись в «Открыть QR».
   - Вариант B: увеличить QR до ~55–65 % ширины экрана и убрать слой (лишний тап).
   - Рекомендация: B для печатной читаемости с другого телефона, но **только после проверки скана**
     на реальном устройстве (первое, что аудит не проверил).
   - Проверка: скан камерой второго телефона, QR 112 px и увеличенный.

**Гейт фазы:** сценарии S1–S5 из отчёта проходят; инвариант «2 тапа до QR» сохранён.

## 6. Риски и откат

| Риск | Вероятность | Что делаем |
|---|---|---|
| Офлайн-экран перекроет уже работающий сценарий с картой | средняя | показываем только при `!getJwt()`, не трогаем ветку «карта есть» |
| Перекомпоновка главной снизит конверсию в QR | средняя | фаза 3 отдельным коммитом, до неё — метрика и скриншоты «до» |
| Увеличение QR сломает вёрстку на 320 px | низкая | QR в `aspect-square` контейнере с `max-h`, проверка на 320 |
| Правки текста разойдутся с промо на витрине | низкая | один словарь `copy/ru.ts` для «Ещё», тексты главной — в компоненте, сверить с лендингом |
| Прод-сборка ведёт себя иначе, чем dev (SW) | высокая | фаза 0 обязательна, проверки только на preview |

Откат: каждая находка — отдельный коммит; проблемный коммит откатывается точечно (`git revert <sha>`)
без затрагивания остальных.

## 8. Что в этот план не входит

- Оплата, предзаказ, бронирование — вне скоупа продукта.
- Заголовок hero по A/B — без метрики не меняем.
- Тёмная тема как фича: закрываем только `color-scheme`, полноценная тема — отдельный проект.
- Правки лендинга/промо-материалов (там всё ещё «6-й стакан» без отличия) — отдельная задача
  для маркетинга, аудит это отметил.
