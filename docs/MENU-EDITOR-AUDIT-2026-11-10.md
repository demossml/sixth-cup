## 1. РЕЗЮМЕ ДЛЯ ВЛАДЕЛЬЦА

Конструктор «Макет меню» — рабочая, но сырая «Фигма для меню». По меркам «владелец без дизайнера» он уже справляется с базовой задачей: собрать лист из каталога, расставить блоки, выгрузить PDF с метками реза и bleed. По меркам Figma/Canva/Adobe Express он пока не дотягивает — в первую очередь по цвету и точности компоновки.

Главное, что работает (проверено руками/API):
- Объёмы товаров корректно печатаются: «250 · 350 · 400 мл / 150 · 180 · 200».
- Замечания перед печатью с именами блоков: «Перед печатью: 2 — Латте 350 мл — не в продаже».
- PDF print/screen, bleed 3 мм, блокеры → 409 → «всё равно скачать» (force).
- Undo/redo (100 шагов), snap к полям, автосохранение, вкладки на телефоне.

5 главных проблем (по убыванию влияния):
1. **Цвет — только 3 нативных color-input** (фон/текст/акцент). Нет HEX-ввода текстом, RGB/HSL, alpha, пипетки, палитр, градиентов. Это главный разрыв с Figma/Canva и прямой запрос владельца.
2. **Дубликаты на живом макете.** Один товар с объёмами разбит на 3 блока («Американо 250/350/400»), «Капучино 250» задвоен. Точечное добавление из каталога не дедупирует.
3. **Слои показывают «Позиция» вместо имени товара** (в dev; в проде имена резолвятся через замечания, но панель слоёв/свойств — нет).
4. **Нет выравнивания/распределения/группировки** — раскладку «по линейке» приходится делать вручную по X/Y.
5. **Создание без названия не валидируется** — тихо становится «Новое меню».

5 быстрых побед (≤ 1 дня каждая): дедуп точечного добавления; HEX-поле + alpha у цветов; валидация пустого названия; имена товаров в слоях; контраст-чек в пикере.

Текущая оценка: **5/10** (работает для «правильно», не для «красиво»). После P0 — **7/10**, после P1 — **8/10**.

### 4.2 Ключевые разрывы (топ-10, по влиянию на нашу задачу)

1. **Цвет без ограничений.** У них: Figma — HEX/RGB/HSL/HSB/CSS/OKLCH + alpha + eyedropper. У нас: 3 нативных `<input type=color>`. → Нужен цвет-модуль (react-colorful/colord) с HEX-полем, alpha, пипеткой (EyeDropper API), палитрой.
2. **Пипетка.** У них: берут цвет с фото/логотипа (Figma — даже за пределами окна). У нас: нет. → EyeDropper API + запасной пикер.
3. **Палитры бренда.** Canva free — 1 палитра 3 цвета, Pro — 100×100. У нас: 3 цвета, нигде не сохраняются между макетами. → `palette` в store + «сохранить в бренд».
4. **Градиенты.** Canva — до 10 стопов бесплатно. У нас: нет. → линейный/радиальный, 2+ стопа.
5. **Выравнивание/распределение.** У них: align left/center/right, distribute. У нас: ручками X/Y. → панель «Выровнять».
6. **Загрузка шрифта.** Canva Pro/Adobe — свой TTF/OTF. У нас: 2 семейства. → upload WOFF2/TTF + подгрузка в PDF (opentype.js/fontkit).
7. **Снапы/направляющие.** Figma — умные направляющие к краям/центрам/другим блокам. У нас: только к полям. → Moveable снапы или свои guides.
8. **Группировка.** У них: сгруппировал → двигаешь вместе. У нас: нет. → group/ungroup.
9. **История версий.** Figma — версии файла. У нас: undo 100 шагов, без снапшотов. → снапшот-история.
10. **CMYK/печать.** Adobe Express — CMYK PDF + bleed. У нас: RGB PDF. → либо ghostscript/littlecms-конвертация на сервере, либо честная пометка «RGB, согласуйте с типографией».

### 4.3 Чем мы обязаны быть лучше Figma (для узкой задачи)

Наша узкая задача — печатное меню кофейни с реальным каталогом. Преимущества, которые надо развивать как продуктовые принципы:

- **Данные вместо рисования.** Товар, цена, объёмы, фото тянутся из каталога. В Figma владелец рисует текст и руками вбивает цену; у нас — блок привязан к product_id. Это главный рычаг.
- **Авто-пересборка при смене цен.** Живые цены + баннер «цены изменились» + «обновить с каталога». В Figma это невозможно.
- **Проверка печатаемости.** Блокеры перед экспортом (нет цены, нет фото, скрыт) с 409 и именами. В Figma — ноль проверок, «сам виноват».
- **Шаблоны под форматы типографий.** A3 фальц, A4, A5, bleed 3 мм, метки реза. В Figma это ручная настройка.
- **Отсутствие пустого холста.** Мастер «собрать из каталога» → сразу готовый лист. Figma/Canva дают пустой холст.

### 4.4 Где Figma объективно лучше и чем закрывать

- Точность компоновки (снапы/направляющие/группы/выравнивание) → P1, библиотеки Moveable + свои guides.
- Цвет/типографика без ограничений → P0–P1, react-colorful + colord + fontsource.
- История версий и коллаборация → P2, снапшоты документа.

### 5.1 Архитектурные развилки (рекомендации)

1. **Остаться на DOM-холсте + точечные библиотеки** (рекомендуется). Мы не переписываем редактор на Konva/Fabric: наш холст уже работает (drag/snap/слои/PDF). Добавляем Moveable+Selecto для трансформаций/снапов/мультивыбора и react-zoom-pan-pinch для зума — без переписывания слоя отрисовки. Полный переход на tldraw/Konva оправдан только при решении «движок сцены» целиком (риск регресса PDF-соответствия).
2. **PDF на сервере оставить** (рекомендуется), но добавить клиентский «предпросмотр печати» как изображение (рендер PNG сервером и наложение). WYSIWYG через headless-браузер — дорого и хрупко; серверный pdfkit уже встраивает шрифты и кириллицу.
3. **Единицы: ввести миллиметры** параллельно процентам (переводный слой), потому что владелец мыслит в мм (поля, отступы, bleed), а не в %. Сейчас хранится в % — ок для адаптива, но UI должен показывать мм.
4. **Undo на патчах immer** (рекомендуется) вместо своей истории — готовое решение для 100-шагового стека с минимумом кода.

### Метрики успеха

- Время «с нуля до готового PDF»: сейчас ~30–40 мин (ручная раскладка) → **≤ 15 мин** после P1.
- Клики на «поменять цвет акцента»: сейчас 4 (клик + picker) → 1–2 (палитра).
- Блокеры на экспорте: сейчас только «нет цены/скрыт» → добавить «фото < dpi», «шрифт < 7pt», «контраст».
- Доля макетов без замечаний — метрика после P0.
- FPS при 100 блоках: замерить в P0 (субъективно сейчас — приемлемо, без фризов на 98 блоках).

### Риски и техдолг

- **Монолит редактора** (`MenuLayoutEditor.tsx` ~1600 строк) — разбить на модули в P1, иначе P2/P3 утонут.
- **Проценты vs мм** — переводить рано (P2-3), до этого координаты в % остаются источником ошибок при смене формата (C1.7 — блоки «улетают»).
- **PDF на сервере** — дублирование логики отображения (DOM vs pdfkit); держать один источник истины (документ) и два рендера, приёмку сверять пиксельно (pixelmatch).
- **Шрифты только 2 семейства** — расширение до 10+ требует проверки кириллицы у каждого (P1-3).
