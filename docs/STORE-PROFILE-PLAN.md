# План: витрина точки — название, точные гео-данные и фото из админки

Дата: 07.11.2026. Ветка `main` (`0d77f5b`). Задача владельца: в **карточке торговой точки с токеном**
(«Касса» → «Токены Эвотор» → карточка точки) указать **название точки, точные гео-данные и фото**, чтобы
гость в PWA мог её найти визуально. Адрес сейчас приходит из Эвотора и должен **меняться в любой момент**.

Касается: `backend`, `frontend-admin`, `frontend` (PWA). Касса APK и PWA-логика заказа — без изменений.

---

## 1. Как сейчас (факты из кода)

| Что | Где | Поведение |
|---|---|---|
| Витрина точки для гостя | `stores` (`name, address, open_time, close_time, lat, lng, hours_json`) | читается `/api/directory` (`directory/routes.ts:189-196`) и `/api/directory/geo` (`:262-280`) |
| Правка витрины | `PATCH /api/admin/stores/:id` (`admin/routes.ts:387-421`) | название, адрес, часы, координаты — **уже можно менять в любой момент**, фото нет |
| Где это в UI | «Касса» → блок **«Кофейни в приложении»** (`Cash.tsx:248+`) | отдельный блок, **не связан** с карточкой точки с токеном |
| Данные Эвотора | `evotor_stores` (`store_uuid, name, address, code, raw_json, sync_enabled, local_store_id`) (`integrations/evotor/db.ts:10-16`) | название и адрес **перезаписываются** при каждом обновлении из облака: `admin/evotorCatalog.ts:118-121`, `PollService.ts:139` |
| Связь Эвотор ↔ витрина | `evotor_stores.local_store_id` | **не заполняется нигде в проде** (только в тестах). Следствия: `storeUuidsForLocalStore()` пуст (`orders/service.ts:221-228`) → у позиций заказа `evotorProductUuid: null`, а резерв бонуса пишется без точки (`orders/benefit.ts:279`) |
| Фото точки | — | поля нет ни в `stores`, ни в ответах API; в PWA кофейня — иконка (`StoresPage.tsx:22-28`) и текст в списке (`StorePickerPage.tsx`) |

Вывод: «адрес из Эватора» гость сейчас не видит вовсе — витрина (`stores`) и данные облака
(`evotor_stores`) живут раздельно, а карточка с токеном показывает облачные значения. Нужно
**свести их в одну карточку**: облако — как источник по умолчанию, владелец — как решающий голос.

---

## 2. Целевая модель

### 2.1. Две сущности, один экран

- `evotor_stores` — **техническая** связь с облаком (uuid, code, sync_enabled, токен). Только чтение из облака.
- `stores` — **витрина для гостя** (название, адрес, гео, фото, часы, ориентир). Пишет владелец.

Связь: `evotor_stores.local_store_id → stores.id` (1 облачная точка ↔ 1 витрина).

### 2.2. Новые поля `stores` (миграция 049, аддитивная)

```sql
ALTER TABLE stores ADD COLUMN photo_url TEXT;          -- 480px WebP (список/карта)
ALTER TABLE stores ADD COLUMN photo_full_url TEXT;     -- 960px WebP (карточка точки)
ALTER TABLE stores ADD COLUMN entrance_hint TEXT;      -- «вход со двора, серая дверь»
ALTER TABLE stores ADD COLUMN phone TEXT;              -- «уточнить, где вы»
ALTER TABLE stores ADD COLUMN name_source TEXT NOT NULL DEFAULT 'manual';     -- manual | evotor
ALTER TABLE stores ADD COLUMN address_source TEXT NOT NULL DEFAULT 'manual';  -- manual | evotor
ALTER TABLE stores ADD COLUMN evotor_name TEXT;        -- снимок облачного названия (для сравнения)
ALTER TABLE stores ADD COLUMN evotor_address TEXT;     -- снимок облачного адреса
CREATE UNIQUE INDEX IF NOT EXISTS idx_evotor_stores_local ON evotor_stores(local_store_id) WHERE local_store_id IS NOT NULL;
```

Rollback: `049_store_profile_rollback.sql` (drop index + колонок).

### 2.3. Правило приоритета (главное)

1. При первом появлении облачной точки создаётся витрина с `name_source='evotor'`, `address_source='evotor'`
   и снимками `evotor_name/evotor_address`.
2. Владелец правит название или адрес вручную → соответствующий `*_source='manual'`.
3. Обновление из облака **никогда** не перезаписывает поле с `*_source='manual'`; для `evotor`-полей —
   обновляет и снимок, и значение. Если облако поменяло адрес, а у нас `manual` — показываем в админке
   подсказку «в Эвоторе: <адрес> · Применить».
4. Фото, ориентир, телефон, часы, координаты — **всегда** ручные (облако их не знает).

## 3. Этапы

Правило серии: один этап → тесты → без регресса → следующий. Коммит/push — по слову владельца.

### S1. Миграция и типы (0.5 ч)

- `backend/src/db/migrations/049_store_profile.sql` + rollback (см. §2.2).
- Типы: `LocalStore` в `frontend-admin/src/pages/Cash.tsx`, `stores[]` в `frontend/src/lib/types.ts`.

**GREEN:** миграция применяется на копии прод-БД, старые данные не меняются, rollback проходит.

### S2. Backend: витрина и связь (1.5 ч)

1. `PATCH /api/admin/stores/:id` — новые поля (`photoUrl, photoFullUrl, entranceHint, phone`), и
   `name`/`address` при изменении ставят соответствующий `*_source='manual'`.
2. `GET /api/admin/stores` и `/stores/:id` — отдают новые поля **и** связанную облачную точку:
   `evotor: { uuid, name, address, code } | null`.
3. `POST /api/admin/stores/:id/link` `{ storeUuid }` — привязка витрины к облачной точке
   (снимает прежнюю привязку этого uuid). `DELETE` — отвязать.
4. `POST /api/admin/evotor/stores/:uuid/local-store` — «создать витрину из облака»: `INSERT INTO stores`
   (name/address из облака, `*_source='evotor'`, организация = организация токена) + привязка.
5. Синхронизация облака: после upsert `evotor_stores` — обновлять снимки и значения только у
   `*_source='evotor'` (единая функция `applyEvotorStoreToShowcase(db, uuid)` в `admin/evotorCatalog.ts`,
   вызов и там, и в `PollService.ensureStores`).
6. `/api/directory` и `/api/directory/geo`: `photoUrl`, `photoFullUrl`, `entranceHint`, `phone`.

**Тесты:** `store-showcase.test.ts` — 8 кейсов: создание витрины из облака; ручной адрес не перетирается
после двух «обновлений из облака»; `evotor`-адрес обновляется; привязка/отвязка; одна витрина на uuid
(уникальный индекс); `photoUrl/entranceHint` доезжают до `/api/directory`; PATCH без `name` не меняет источник.

### S3. Админка: поля в карточке точки с токеном (2 ч)

В `StoreCard` (`frontend-admin/src/pages/Cash.tsx:19+`) — блок **«Как видит гость»**:

| Поле | Контрол | Подсказка |
|---|---|---|
| Название | `Input` + селектор источника `Из Эвотора / Своё` | «Так точка называется в приложении» |
| Адрес | `Input` + источник | «Улица, дом — как в картах» |
| Координаты | два поля + «Ссылка из карты» → «Заполнить» | уже реализовано (`lib/coords.ts`) |
| Фото точки | превью 4:3 + «Загрузить фото» / «Убрать» | «Фасад с вывеской, днём» |
| Ориентир | `Input` (120 симв.) | «Вход со двора, серая дверь» |
| Телефон | `Input` (tel) | необязательно |
| Часы | как сейчас | — |

- Если витрины ещё нет — кнопка **«Создать витрину точки»** (S2.4), после неё поля активны.
- Ссылка «Открыть в приложении» → `/pick-store` (локально) или прод-URL.
- Старый блок «Кофейни в приложении» **убираем** из «Кассы» (поля переехали в карточку точки),
  оставляем только создание точки, у которой нет пары в облаке (редкий случай).
- Загрузка фото — существующий `uploadFile()` (JPEG/PNG/WebP ≤ 2 МБ → WebP 480/960).

**GREEN:** правки видны в `/api/admin/stores`; фото загружается и показывается превью; после
«Обновить из Эвотора» ручной адрес остаётся.

### S4. PWA: точка с фото (1.5 ч)

1. `StorePickerPage`: карточка точки = фото 4:3 (или плейсхолдер с иконкой), название, адрес, часы,
   «Ориентир», кнопки «Маршрут · <карта>» / «На карте». Фото грузится `loading="lazy"` из 480-варианта,
   по тапу — 960 в шите «Как найти».
2. Схема города: у выбранной точки подпись с фото-миниатюрой 40×40 (или только имя при отсутствии фото).
3. `StoresPage` («Ещё» → «Кофейни»): список с фото-миниатюрой 72×72, адрес, часы.
4. Экран заказа (`OrderQrScreen`): строка «Забрать: <название> · <адрес>» + миниатюра фото.

**GREEN:** на телефоне точка видна с фото; при отсутствии фото — аккуратный плейсхолдер (ice-градиент + маскот).

### S5. Предел «одна точка — один uuid» и подсказки (0.5 ч)

- В админке: если у витрины нет связи — жёлтая плашка «Точка не связана с кассой: позиции заказа уйдут
  без UUID товаров» + кнопка «Привязать к точке Эвотор».
- Если облачная точка изменила адрес, а у нас ручной — строка «В Эвоторе: … · Применить».

**GREEN:** новая точка без связи подсвечена; «Применить» переносит адрес и ставит `address_source='evotor'`.

### S6. Тесты и приёмка (1 ч)

- backend: `store-showcase.test.ts` (S2) + прогон полного набора;
- admin: юнит на `coords.ts` (есть), на источник полей (если вынесем в `lib/storeProfile.ts`);
- PWA: `menuModel` (часы) + ручной прогон;
- живой прогон: облачная точка → витрина → адрес вручную → повторный синк → адрес не изменился;
  фото загружено → видно в PWA на трёх экранах;
- `npm run typecheck && npm run build`, все тесты, `scripts/e2e-smoke.mjs`.

## 5. Риски и как их снимаем

| Риск | Решение |
|---|---|
| Синк из облака затирает ручной адрес | `*_source` + тест «два синка подряд не меняют `manual`» |
| Две витрины на одну облачную точку | уникальный индекс `evotor_stores(local_store_id)` |
| Фото весит много / тормозит список | 480 WebP для списка, 960 только в шите, `loading=lazy` |
| Владелец снял точку с продажи в Эвоторе | витрину не удаляем: гость видит точку, заказ не уходит (существующий `soldOut`/закрытая точка) |
| Старый блок «Кофейни» и новая карточка правят одно и то же | блок убираем, единственный вход — карточка точки |
| Гость закэшировал каталог | обновление каталога по pull-to-refresh; фото — обычные URL с кэшем браузера |

## 6. Решения, которые нужны от владельца

1. **Фото: одно или несколько?** Рекомендую **одно главное** (фасад с вывеской) — быстрее и понятнее;
   галерею можно добавить позже без ломки схемы.
2. **Показывать фото в списке выбора точки?** Рекомендую **да** (миниатюра слева в карточке) — это и есть
   «найти визуально».
3. **Название точки: одно для гостя и для кассы или разное?** Рекомендую **разное разрешить**:
   в Эвоторе «Точка 1», гостю — «6.7 Coffee на Ленина» (именно это и даёт `name_source`).

## 7. Что не входит в этот план

- Реальная фотография — контент владельца (нужны файлы).
- Карта с тайлами (Яндекс/Google SDK) — остаётся схема + deep links в карты.
- Касса APK: фото точки на чеке/QR не требуется.
- Часы работы из Эвотора — их там нет, остаются ручными.
