# ПРОМПТ ДЛЯ АГЕНТА КАССЫ (APK): очередь предзаказов, статусы, «подтянуть в чек»

Репозиторий: **`demossml/evotor-app`** (Android, Kotlin).
Смежный репозиторий: `demossml/sixth-cup` (backend + PWA) — **не менять его в этой задаче**.
Документ-партнёр: [`PREORDER-ROLLOUT-PLAN.md`](./PREORDER-ROLLOUT-PLAN.md).

> Задача: касса должна видеть предзаказы из PWA, принимать их, показывать гостю статус через backend
> и «подтягивать» состав в чек Эвотора. Оплата и фискализация — как сейчас, только на кассе.

---

## 0. Жёсткие правила (нарушение = задача не принята)

1. **Не менять** лояльность, `ReceiptValidator`, скидки, ваучеры, сканер QR карты, `DiscountCalc`,
   `FiscalLines`, `ReceiptPlan`. Правки — только в новых файлах очереди заказов и в месте вызова из `MainActivity`.
2. **Не менять цены** в заказе: сумма из API — оценка. Цену и чек считает касса по номенклатуре Эвотора.
3. **Не создавать заказы** из APK (`POST /api/orders` — только гость).
4. **Не менять** контракт `/api/devices/loyalty/resolve`, `extras.sc` (кроме добавления `ord`), `v=2`, `c`, `op`, `free`, `cb`.
5. Обязательные заголовки device-запросов: `X-Device-Token: <token из enroll>`, `Content-Type: application/json`.
   Авторизация прокси (`Authorization`) — как в существующем коде для device-запросов.
6. Ничего не «додумывать»: если в ответе нет поля — считай его `null` и действуй по таблицам ниже.
7. Версия: `versionCode +1`, `versionName` по схеме проекта (например `5.3.1-preorder`). В отчёт — оба значения.
8. Секреты и токены не логировать. В логи — только `orderId` (первые 8 символов) и `shortCode`.

## 1. Контракт backend (актуальный; проверять `ok` и HTTP-код)

Базовый URL и авторизация — те же, что у уже работающих `/api/devices/*` (прокси Эвотор).
Деньги: `estimateTotal` — в рублях (как `products.price`).

### 1.1. Список активных заказов точки

```
GET /api/devices/orders/active
→ 200 { ok: true, orders: [ { id, shortCode, status, createdAt, estimateTotal, itemsCount } ] }
→ 401 { ok: false, error: "unauthorized" }
```
Активные: `draft | accepted | cooking | ready`. Отсортировано от новых к старым, максимум 100.

### 1.2. Получить заказ по QR или по коду

```
GET /api/devices/orders/resolve?oid=<uuid>      // из QR заказа (payload ord1.* → внутри oid)
GET /api/devices/orders/resolve?code=<123456>   // 6 цифр, ввод вручную
→ 200 { ok: true, order: OrderOut }
→ 400 { ok: false, error: "bad_request" }      // нет ни oid, ни code
→ 401 { ok: false, error: "unauthorized" }     // нет/протух X-Device-Token
→ 403 { ok: false, error: "wrong_store" }      // заказ другой точки
→ 404 { ok: false, error: "not_found" }
→ 409 { ok: false, error: "already_paid" }     // уже оплачен
→ 409 { ok: false, error: "rejected" }         // отклонён/отменён
→ 410 { ok: false, error: "expired" }          // истёк срок
```

`OrderOut` (все поля, которых может не быть — `null`):
```json
{
  "id": "uuid",
  "shortCode": "123456",
  "storeId": 1,
  "status": "accepted",
  "createdAt": "2026-11-07T10:00:00.000Z",
  "expiresAt": "2026-11-07T10:30:00.000Z",
  "etaReadyAt": "2026-11-07T10:07:00.000Z",
  "etaMinutes": 7,
  "serverNow": "2026-11-07T10:01:00.000Z",
  "estimateTotal": 650,
  "currency": "RUB",
  "cardId": "0007",
  "items": [
    {
      "lineId": "uuid",
      "productId": "910",
      "evotorProductUuid": "evo-uuid-910",
      "name": "Капучино 300 мл",
      "quantity": 1,
      "volumeLabel": "300 мл",
      "configText": "300 мл · кокосовое",
      "unitPriceEstimate": 650,
      "modifiers": [
        { "group": "milk", "id": "2", "name": "Кокосовое", "priceEstimate": 0,
          "sendToReceipt": true, "evotorUuid": "evo-uuid-coconut" }
      ]
    }
  ],
  "warnings": []
}
```
Правила разбора: `evotorProductUuid == null` → позицию нельзя положить в чек, показать предупреждение
`«Нет UUID на точке — добавьте товар в выгрузку»` и заблокировать «В чек».
`modifiers[].sendToReceipt = false` → в чек не добавлять (обычное молоко, бесплатные опции).
`modifiers[].evotorUuid == null` при `sendToReceipt = true` → предупреждение, но позицию разрешить,
опцию добавить вручную (так же, как сейчас кассир добавляет добавки).

### 1.3. Смена статуса

```
PATCH /api/devices/orders/:id/status   { "status": "accepted" | "cooking" | "ready" }
→ 200 { ok: true, order: OrderOut }
→ 400 { ok:false, error:"bad_request" }   // статус не из списка
→ 403 wrong_store | 404 not_found
→ 409 { ok:false, error:"invalid_transition", from, to }  // назад/через отмену нельзя
```
Допустимые переходы: `draft→accepted`, `accepted→cooking`, `accepted→ready`, `cooking→ready`.
`accepted→ready` разрешён намеренно: кассир может подтвердить готовность раньше прогноза ETA
(ETA — прогноз, а не запрет). Назад и из `paid/rejected/cancelled/expired` — нельзя.
Повторный вызов с тем же статусом — **не** ошибка на стороне клиента: просто перечитать заказ.

### 1.4. Уточнить ETA (опционально, P1)

```
POST /api/devices/orders/:id/eta  { "etaMinutes": 5 }
→ 200 { ok: true, order: OrderOut }
```

### 1.5. Отклонение и оплата

```
POST /api/devices/orders/:id/reject    { "reason": "нет молока" }
→ 200 { ok: true } | 403 wrong_store | 404 | 409 invalid_transition

POST /api/devices/orders/:id/mark-paid
→ 200 { ok: true, order }
→ 409 { ok:false, error:"invalid_transition" }   // если статус не accepted|cooking|ready
```

### 1.6. Привязка к фискальному чеку

В `extras.sc` (и в дубль под `extras[APP_UUID].sc`, как сейчас) добавить **один** ключ:
```json
"ord": "<orderId uuid>"
```
Ничего больше в `sc` не менять. Backend сам свяжет заказ с SELL (после Stage C backend).

## 2. Экраны и поведение

### 2.1. Баннер очереди на главном экране кассы

- Показывается, если `GET /orders/active` вернул ≥1 заказ **и** текущий экран — главное меню кассы.
- Компактная полоса вверху: `● Заказ 123456 · 2 поз. · ~4 мин` (или «Готовится», «Готов»),
  справа счётчик `N` если заказов больше одного.
- Тап → экран «Предзаказы». Свайп/тап на конкретный заказ → панель заказа.
- Опрос `GET /orders/active` каждые **10 с**, только когда экран в foreground (`onResume`/`onPause`).
- Нет заказов → баннера нет, никакого пустого места.

### 2.2. Экран «Предзаказы» (очередь)

- Список карточек: `код`, `статус`, `осталось ~N мин` (из `etaReadyAt` и `serverNow`), `сумма-оценка`, `кол-во позиций`.
- Сортировка: `draft` сверху (их ждут), затем `accepted`, `cooking`, `ready`; внутри — по `createdAt`.
- Refresh: pull-to-refresh + авто 10 с. Pull — вручную.

### 2.3. Панель заказа (после скана QR/ввода кода)

Обязательные элементы:
1. `Заказ 123456` + точка + статус + остаток ETA.
2. Состав: `name`, `configText`, `qty × unitPriceEstimate`, строка `Оценка гостя: N ₽`
   (подпись: «Финальная цена — по номенклатуре Эвотора»).
3. Карта лояльности, если `cardId != null`: «Карта 0007 привязана» (лояльность применяется как сейчас,
   при добавлении в чек — существующим loyalty-resolve, **без изменений**).
4. Кнопки по статусу:

| Текущий статус | Кнопки |
|---|---|
| `draft` | **«Принять»** (PATCH `accepted`), «Отклонить» |
| `accepted` | **«Готовится»** (PATCH `cooking`), «Готов» (PATCH `ready`), «В чек», «Отклонить» |
| `cooking` | **«Готов»** (PATCH `ready`), «В чек», «Отклонить» |
| `ready` | **«В чек»**, «Отклонить» (только если не оплачен и не начат чек) |
| `paid` | экран «Оплачен», кнопок нет, «Закрыть» |

5. После `mark-paid` — экран «Оплачен · Заказ 123456» и возврат в очередь.
6. Если backend вернул `etaReadyAt` — показать «Готов через ~N мин»; по истечении — «Готовим, уточняем».
   Статус `ready` может прийти **сам** (авто по таймеру) — экран должен обновиться без действий кассира.

### 2.4. «В чек» (подтянуть состав)

1. Для каждой позиции с `evotorProductUuid`: добавить в существующую корзину кассы товар по UUID,
   `quantity`, цена — из номенклатуры (существующий механизм поиска товара по uuid).
2. Для каждого модификатора с `sendToReceipt = true` и `evotorUuid != null`: добавить отдельной позицией
   по UUID (бесплатные/`sendToReceipt=false` — пропустить).
3. Показать диалог подтверждения: «Добавлено N позиций. Сумма по кассе: X ₽» + предупреждения.
4. Если у позиции нет `evotorProductUuid` — позиция пропускается, кассир добавляет вручную,
   в диалоге явно: «Капучино 300 мл — нет UUID на точке».
5. В чек при SELL положить `sc.ord = orderId` (см. 1.6).
6. После успешного SELL — `POST /orders/:id/mark-paid`. Если SELL не прошёл — `mark-paid` **не** вызывать.

### 2.5. Сканирование

- QR заказа: payload начинается с `ord1.`. Разобрать base64url-часть (JSON), взять `oid` → `resolve?oid=`.
- Если отсканирован **QR карты лояльности** (`t='c'`) — поведение прежнее, заказы не трогаем.
- Ввод 6 цифр — `resolve?code=`.
- Ошибки 403/404/409/410 — русские тексты по коду (см. 1.2), без стектрейсов в UI.

## 3. Матрица ошибок (обязательно обработать все)

| Ситуация | Что делает APK |
|---|---|
| нет сети / таймаут | «Нет связи с сервером» + «Повторить», заказ не теряется |
| `401` | «Терминал не авторизован. Перепривяжите кассу» |
| `403 wrong_store` | «Заказ оформлен для другой кофейни» |
| `404` | «Заказ не найден» |
| `410 expired` | «Срок заказа истёк» + «Закрыть» |
| `409 already_paid` | «Заказ уже оплачен» + обновить статус |
| `409 rejected` | «Заказ отклонён или отменён» |
| `409 invalid_transition` | перечитать заказ и перерисовать кнопки |
| пустой `orders` | баннер и экран очереди пустые, без ошибок |

## 4. Тесты (обязательные, без них задача не принимается)

Unit (JVM, как существующие тесты проекта):
1. Парсер `ord1.*` → `oid`; битый payload → `null`, без исключения.
2. Маппер статусов: `дraft/accepted/cooking/ready/paid` → подписи и доступные кнопки (таблица 2.3).
3. Остаток ETA: `etaReadyAt`−`serverNow`; `etaReadyAt == null` → «уточняем»; отрицательный → «уточняем».
4. Фильтр модификаторов: `sendToReceipt=true` + `evotorUuid` → в чек; `false` → пропуск.
5. Позиция без `evotorProductUuid` → помечена как «нельзя добавить», чек не ломается.
6. Ошибки 401/403/404/409/410 → тексты и отсутствие падения.

Ручная проверка на терминале (чек-лист в отчёт):
- [ ] заказ из PWA виден в баннере ≤ 10 с
- [ ] «Принять» → у гостя в PWA статус «Принят»
- [ ] «Готовится» → у гостя «Готовится ~N мин»
- [ ] авто-«Готов» по таймеру без действий кассира
- [ ] «В чек» → позиции и платные опции в корзине
- [ ] SELL → `mark-paid` → у гостя «Оплачен»
- [ ] QR карты лояльности по-прежнему открывает лояльность (регресс)
- [ ] заказ другой точки → 403, ничего не добавлено

## 6. Зависимости и порядок

1. Сначала на backend выкатываются **Stages A–C** из `PREORDER-ROLLOUT-PLAN.md`
   (ETA, `active`, бан, UUID позиций/модификаторов, админ-страховка).
2. Затем APK: очередь, статусы, «В чек», `sc.ord`, `mark-paid`.
3. Если backend ещё старой версии (нет `etaReadyAt`/`evotorUuid` в модификаторах) — APK обязан работать
   без падений: «уточняем» вместо ETA, опции добавляются вручную. Совместимость вниз — обязательна.
