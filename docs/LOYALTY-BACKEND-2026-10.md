# Лояльность: что изменилось (28.10.2026)

Короткая памятка по изменениям backend-серии: привязка номера очереди, сторно без `sc`,
ручная корректировка, повтор сбойных чеков, стоп-лист карт, разделение источников кэшбэка.

Каналы записи по-прежнему описаны в [LOYALTY-CHANNELS](./LOYALTY-CHANNELS.md).

## 1. Номер очереди привязывается к документу Эвотора

- `extras.sc.ord` — orderId, `extras.sc.qn` — публичный номер (только для логов).
- Привязка выполняется в `handleSell` **сразу после разбора `sc`**, до проверки карты:
  номер получит связь с документом даже если карта не распознана.
- `bindQueueNumber(orderId, { evotorDocumentUuid, fiscalDocumentNumber })` переводит номер
  в `BOUND`. Ошибка привязки влияет только на лог — лояльность не страдает.
- Повторный poll того же `doc_id` безопасен: связь уже стоит, номер не «воскресает» после отмены.

## 2. Возврат сторнирует лояльность даже без `extras.sc`

- `processLoyalty`: если у `PAYBACK` нет `sc`, но по базовому чеку (`baseDocumentUUID`)
  есть `loyalty_ops.kind='SELL'`, обработка идёт обычным путём — чашки, бесплатные и кэшбэк
  откатываются.
- Если базовой продажи с лояльностью нет — документ помечается `PROCESSED` без изменений балансов.
- Идемпотентность прежняя: повторный `PAYBACK` не сторнирует дважды (`loyalty_ops` PK).

## 3. Ручная корректировка балансов

`POST /api/admin/customers/:id/loyalty-adjust`

```json
{ "cupsDelta": 3, "freeUsedDelta": 0, "cashbackDeltaKop": 5000, "reason": "компенсация за сбой" }
```

- Только роль **owner**: manager и viewer получают 403.
- `reason` обязателен (минимум 3 символа).
- Пишется строка `loyalty_ledger` с `operation='ADJUSTMENT'`, `source_type='ADMIN_ADJUST'`.
- Аудит (`admin_audit`) хранит причину, старые и новые значения и **фактически применённые** дельты.
- Отрицательный итог кламплится в ноль: если применять нечего — 400, пустых записей не появляется.

## 4. Сбойные чеки: тело сохраняется, повтор из админки

- Для документов, ушедших в `FAILED`, сохраняется `evotor_docs.raw_json` (только для сбойных).
  После успешной обработки raw стирается — таблица не превращается в архив чеков.
- `GET /api/admin/loyalty/failed` — список сбоев: точка, тип, `attempts`, `last_error`,
  `next_retry_at`, признак наличия тела.
- `POST /api/admin/loyalty/failed/:docId/retry?storeUuid=…` — повтор: сначала сохранённое тело,
  затем узкое окно Cloud (±6 ч) для старых сбоев без raw.
- Повтор идемпотентен: уже обработанный документ вернёт `PROCESSED` без второго начисления.

## 5. Игра и рефералка больше не смешиваются

- Награды игры пишутся в `cashback_ledger` с `receipt_id = 'game:<sessionId>'`.
- `friendsView` (карточка гостя), `GET /api/admin/referrals` и пары рефералов считают только
  реферальные начисления — игровые не входят в «кэшбэк от друзей».
- В истории PWA награда за игру идёт отдельной строкой «Награда за игру».

## 6. Стоп-лист карт

- `POST /api/admin/cards/:cardId/block` `{ reason }` — блокировка (ключ — строковый `card_id`).
- `DELETE /api/admin/cards/:cardId/block` — разблокировка (404, если карта не заблокирована).
- Проверяется в двух местах: `resolve` (возвращает `card_blocked`) и `handleSell`
  (на случай прямого вызова API, пишет спор `card_blocked`).
- Повторная блокировка обновляет причину, а не создаёт дубль.

## 7. История для PWA

`GET /api/sync/history` — контракт аддитивный, старые поля на месте. Добавлено:

| Поле | Смысл |
|---|---|
| `freeDelta` | сколько бесплатных чашек списано (`−1` на продаже) или возвращено (`+1` на возврате) |
| `reason` | почему не начислено: `bonus_clamped` (бонус урезан), `free_applied` (списана бесплатная), `no_cup_positions` (позиции не участвуют в прогрессе), иначе `null` |

Строки типов `cashback_spend`, `cashback_back`, `referral`, `referral_reversal`, `game_reward`
не изменились.

## Что осталось на APK / PWA

- **APK:** передавать `ord` и `qn` в `extras.sc`; при возврате по возможности прикладывать `sc`.
- **PWA:** показать `freeDelta` и `reason` в истории (админка и API уже готовы).
- Ручной код карты по-прежнему **не** даёт права списывать бонусы — это не менялось.
